Real data arrives dirty. Today you read a file off the disk, decide line by line what is usable, keep a record of what you rejected and why, and write your results back out to a second file.

2The file, and the boundary20 minutes

Every program that reads from outside itself has a boundary, and the boundary is where programs break. Two things can go wrong before you even see a number: the file might not exist, and a line might not be a number.

try and except let you say what to do instead of crashing.

def read_lines(filename):
    """Return every line in the file, or an empty list if it is missing."""
    try:
        handle = open(filename, "r")
    except FileNotFoundError:
        print(f"no file called {filename}, so there is nothing to read")
        return []
    lines = handle.readlines()
    handle.close()
    return lines
Predict first. Why is handle.readlines() outside the try block rather than inside it?

Because the only error being handled is the file not existing. Once open succeeds, a failure in readlines is a different problem and should not be quietly swallowed by an except written for something else.

Catch one named thing. Never write a bare except:. It hides bugs you have not met yet.

def clean(lines):
    """Return the numbers we could read, plus the lines we could not."""
    good = []
    rejected = []
    for raw in lines:
        text = raw.strip()
        text = text.replace(",", "")
        if text == "":
            rejected.append((raw, "blank"))
        else:
            try:
                value = int(text)
            except ValueError:
                rejected.append((raw, "not a number"))
            else:
                if value < 0:
                    rejected.append((raw, "negative"))
                else:
                    good.append(value)
    return good, rejected
Predict first. Thirteen lines go in. How many numbers come out, and what is their total? You have seen this total before.
verified output
lines in the file: 13
kept: [41, 58, 33, 58, 12, 77, 58, 60, 29, 77]
kept 10, rejected 3
rejected lines and why:
  'twelve\n' -> not a number
  '\n' -> blank
  '-9\n' -> negative

readings_report.txt now says:
kept 10 readings
rejected 3 lines
total 503
average 50.3

503 and 50.3. That is session 1's list, exactly. The dirty file held the same ten readings you have been working with since the first day, buried in three lines of rubbish.

Notice else attached to try. It runs only when no exception happened, which keeps the negative check out of the block that is watching for ValueError.

The rejected list is the point. A program that silently drops three lines and reports an average is worse than one that crashes, because you will believe it. Say what you threw away and why, every time.

What to watch for

Two failures to expect. First, int(" 33") actually works in Python, so some students will conclude .strip() is pointless. It is not: int("77,") fails, which is why the comma is in the file. Second, students will write a bare except: because it is shorter. Do not allow it.

The reveal that this is session 1's data lands well if you do not telegraph it. Let them compute 503 and notice.
